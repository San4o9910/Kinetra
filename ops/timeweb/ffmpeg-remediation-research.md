## Additional verification and reconciliations

The exact tagged source was additionally compared with the upstream patch hunks for 58049 and 64830–64835. RASC checks byte room before its 32-bit DLTA accesses; VobSub reuses stream IDs and bounds the queue; Vulkan HEVC checks HRD counts; NVDEC no longer frees the same sep-ref context on its error path; DTS-HD bounds core size; RTP/ASF checks minimum object size; ADX refreshes channel state. All relevant added fix lines are present in the tagged files, and the NVDEC obsolete error-path cleanup is absent from the affected function. This was source inspection, not execution of CVE reproductions.

For CVE-2026-8461, [FFmpeg's security page](https://ffmpeg.org/security.html) groups three master fixes. All three are ancestors of 9.0.1: the table's `c23d4da3128c279b714b282e6ec292e8755007e3`, [5806e8b9f34f1b0663b3017ef9dd1aa5d08116d1](https://api.github.com/repos/FFmpeg/FFmpeg/compare/5806e8b9f34f1b0663b3017ef9dd1aa5d08116d1...bf1b838f2ab88b4f8fd83443325c782ea0e0f7fa) (+877/−0), and [374b726ffa878ee1cadb987bd1e1e20cc7ed8845](https://api.github.com/repos/FFmpeg/FFmpeg/compare/374b726ffa878ee1cadb987bd1e1e20cc7ed8845...bf1b838f2ab88b4f8fd83443325c782ea0e0f7fa) (+878/−0). Debian also documents backports to n8.1.2, n7.1.5, and n5.1.10.

The reconciled JSON is a capture of tracker notes, not a curated fix-only list: its `commits` arrays for 70628 and 70632 also contain the introducing commits `c6ec28b18cd1eb7d39e6163137367f2d1c62aa7c` and `1006a2151236f9235bf02822f263b3fb0532111e`. Those are not fixes. For 8461 the array omits master `c23d4da…` although the notes contain it, because that tracker URL lacks the usual `/commit/` segment. The table above explicitly resolves these ambiguities.

The first web-cache copy of Debian's 58049 record omitted fix notes; the fresher record captured by the image agent includes the same master and release fixes independently found in official FFmpeg history. No code/hash disagreement remains. Debian package-status tables and broad affected-version descriptions for 64831/64832 are not used as proof of upstream 9.0.1 status.

## Practical consequence

A replacement must use the reviewed 9.0.1 source/tag, retain verifiable source and build provenance, and pass the existing vulnerability and media-functional gates. Keep these fixes separate from the remaining OS/ImageMagick findings. Removing package records, ignoring findings, or treating a source version string as sufficient proof would not establish remediation. The current vulnerable image is not approved by this research.
